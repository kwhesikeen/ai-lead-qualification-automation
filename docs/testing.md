# CedarLead Testing and Regression

## 1. Overview

CedarLead includes an automated regression-testing system designed to verify the Intake API, Status API, QA support workflow, lifecycle rules, idempotency behavior, authentication controls, and privilege separation.

The regression system uses:

- Postman Desktop.

- Postman Collection Runner.

- Postman CLI.

- PowerShell.

- A dedicated CedarLead QA Support API.

- Dynamically generated test data.

The current full regression suite contains:

```text
16 requests
64 assertions
```

Latest validated result:

```text
64 passed
0 failed
0 errors
```

---

## 2. Testing Objectives

The regression suite is designed to verify that changes to CedarLead do not break:

- Lead intake.

- Required-field validation.

- Duplicate protection.

- Dynamic lead creation.

- Dynamic lead lookup.

- Lifecycle transitions.

- Lifecycle idempotency.

- Missing-lead handling.

- Invalid-transition protection.

- Intake authentication.

- Status authentication.

- QA authentication.

- Credential privilege separation.

The suite is intended to be repeatable without manually editing real `leadId` values between runs.

## 5. Collection Variables

The regression collection generates and reuses the following collection variables:

```text
qaRunId
qaEmail
qaMessageTag
qaLeadId
qaContactedFollowUpAt
```

Purpose:

```text
qaRunId
-> uniquely identifies one automated run
qaEmail
-> provides a fresh lead email for every regression execution
qaMessageTag
-> ensures test content is unique
qaLeadId
-> stores the dynamically generated CedarLead lead identifier
qaContactedFollowUpAt
-> stores the lifecycle idempotency baseline timestamp
```

These variables allow the test suite to avoid hard-coded real lead IDs.

## 6. Dynamic Test Data Generation

The first Intake request generates fresh QA data using a Postman Before-request script.

Example logic:

```javascript
const timestamp = Date.now();
const randomSuffix = Math.floor(Math.random() * 100000);
const runId = `${timestamp}-${randomSuffix}`;
const qaEmail = `cedarlead.qa.${runId}@example.com`;
const qaMessageTag = `QA-RUN-${runId}`;
pm.collectionVariables.set("qaRunId", runId);
pm.collectionVariables.set("qaEmail", qaEmail);
pm.collectionVariables.set("qaMessageTag", qaMessageTag);
pm.collectionVariables.set("qaLeadId", "");
```

This creates a fresh lead identity for every complete regression run.

Example generated email:

```text
cedarlead.qa.1793528897184-68783@example.com
```

## 8. Asynchronous Intake Challenge

The Intake API returns HTTP 202 before the full workflow finishes.

The asynchronous processing chain can include:

```text
duplicate evaluation
deterministic scoring
OpenAI request
Ollama fallback
Google Sheets write
lifecycle initialization
email processing
```

Therefore the newly generated `leadId` is not available directly in the initial Intake response.

CedarLead solves this testing problem with a dedicated QA Support API.

---

## 9. QA Support API

Endpoint:

```text
POST /webhook/qa-lead-lookup
```

Authentication:

```text
QA API Key
```

The QA Support API accepts:

```json
{
  "email": "cedarlead.qa.example@example.com"
}
```

and searches the Leads sheet for the QA-generated email.

When found, it returns:

```json
{
  "success": true,
  "status": "found",
  "leadId": "CL-20261101-409",
  "email": "cedarlead.qa.example@example.com",
  "lifecycleStatus": "NEW"
}
```

Postman then stores:

```text
leadId -> qaLeadId
```

using:

```javascript
pm.collectionVariables.set("qaLeadId", body.leadId);
```

---

## 10. QA Polling Behavior

Because Intake processing is asynchronous, the QA Support API uses bounded polling.

Maximum attempts:

```text
8
```

Wait interval:

```text
5 seconds
```

Conceptual sequence:

```text
Attempt 1 -> immediate
Attempt 2 -> wait 5 seconds
Attempt 3 -> wait 5 seconds
Attempt 4 -> wait 5 seconds
Attempt 5 -> wait 5 seconds
Attempt 6 -> wait 5 seconds
Attempt 7 -> wait 5 seconds
Attempt 8 -> wait 5 seconds
```

If the lead is found:

```text
HTTP 200
```

If it is not found before the retry limit:

```text
HTTP 404
```

Invalid lookup requests return:

```text
HTTP 422
```

The polling loop is bounded so the workflow cannot execute indefinitely.

## 13. Lifecycle Idempotency

CedarLead tests same-state lifecycle requests using two consecutive CONTACTED operations.

### Baseline Request

The first repeated CONTACTED request stores:

```text
nextFollowUpAt
```

as:

```text
qaContactedFollowUpAt
```

### Repeat Request

The second repeated CONTACTED request verifies:

```text
previousStatus = CONTACTED
lifecycleStatus = CONTACTED
owner unchanged
nextFollowUpAt unchanged
```

The assertion compares the current timestamp to:

```text
qaContactedFollowUpAt
```

A changed timestamp would fail the regression test.

1\. Add the request to the correct collection folder.

2\. Avoid hard-coded real lead IDs.

3\. Reuse generated collection variables where possible.

4\. Use deterministic test data.

5\. Add explicit HTTP status assertions.

6\. Add business-contract assertions.

7\. Save the request before running the Collection Runner.

8\. Run the relevant folder.

9\. Run the complete 16-request or expanded suite.

10\. Verify CLI execution.

11\. Update this documentation.

## 32. Test Design Principles

CedarLead tests follow these principles:

```text
repeatable
state-aware
dynamic
isolated where possible
explicit
negative-case aware
security-aware
idempotency-aware
```

Tests should verify business behavior, not merely HTTP status codes.

For example:

```text
422 with correct key
```

proves the authentication layer passed and application validation executed.

Similarly:

```text
409 CONTACTED -> WON
```

proves lifecycle policy enforcement rather than generic endpoint availability.
